# Longshot on the ROG Ally: overnight report (2026-11-14, 00:07-08:10)

The Ally was plugged in with the screen on for every run. All runs are at the 8 GB UMA frame buffer the Ally has had since the reboot at 23:34.

The route has three spots: Kokiri, Hyrule Field and Market Town. Each spot shows four camera views for 20 s each.

FG 2x is on, so about 2 frames are shown per game frame. p99 is the 99th-percentile time between shown frames (`bench\frames_report.py`).

Run-to-run noise is about ±5 ms in p99 and ±1 game fps. Only differences larger than that count. Full details are in HANDOVER.md.

## What limits the frame rate
- **CPU and memory bound, not GPU and not thermal.**
  - GPU 3D busy averages 55-69%, at 17-21 ms of GPU time per game frame.
  - APU 92-95 °C, passive limit 100%, throttle reasons 0 in every run.
  - The game's job threads and the readback waits set the pace.
- **Hitches** (12-30 frames over 100 ms per 80 s spot) come at view turns and loads, while the game pages memory.
  - Page reads run at about 2,000/s, and free RAM goes near 0.
  - This is not shader compiling: the pipeline and driver caches are built.
- **Freezes at 8 GB UMA.** Windows sees 7.9 GB of RAM and the shared GPU heap is 3.9 GB.
  - Area loads fill that heap, and `vkQueueSubmit` fails with -2 (out of device memory).
  - The game then waits forever for work that never ran.

## What was found online (`research-2026-11-14.md`)
- Readback waits are a known CPU stall on integrated GPUs.
  - Longshot PR #238 (merged 11-14) added `RX_VK_READBACK_LATE=newest`: +14-25% on Steam Deck.
  - Risk: a stale exposure value, seen as a white flash.
- Older Hookshot Ally guides recommend an 8 GB UMA. That predates Longshot's imported memory pools, which live in the shared heap.
- The sleep, spin and virtual-core switches (`HOS_SHORT_SLEEP_POLLERS`, `HOS_SPIN_*`, `HOS_RESERVE_CORE`) are suspects for the CPU regression after build d7a7306.
- Longshot already has these:
  - FSR 3.1 (`dlss=3`);
  - its own 2x frame generation with an even-spacing pacer;
  - Anti-Lag 2 (VK_AMD_anti_lag);
  - pipeline caches.

## Old play build vs Longshot, same night, same 8 GB UMA (q8)
- **The old play build (a copy of it) froze on 4 of 4 Hyrule Field / Town loads,** with the same `submit failed (-2)`.
  - The build you play now will freeze entering those areas until UMA is back at 4 GB.
- In Kokiri the old build got 45.5 / 39.7 game fps, against Longshot's 37.8 / 38.4. Longshot is now about 10% behind (it was about 20%).
- Measured over the same window, Longshot is as smooth or smoother:
  - p99: 71-81 ms against 82-83 ms;
  - frames over 100 ms: 73-88 against 92-96.

## Not met yet
- **720p internal upscaled by FSR 3.1 to 1080p at a hitch-free 40-60 fps** isn't reachable on this chip with this build.
  - The 1080p output costs 28% (about 26 fps).
  - The best setup reaches about 37 game fps (about 70 shown with FG). Each spot still has hitches at turns and loads.

## What you can do (your settings, not changed by me)
1. **Set the UMA frame buffer back to 4 GB** in the BIOS or Armoury Crate. This fixes the freezes for both builds.
   - The first start of each build afterwards rebuilds the driver's shader cache, which takes 30-40 min.
2. Try Longshot (`C:\Users\Admin\Games\Longshot-Ally`). Its `longshot_env.txt` now has both kept changes. The old file is in `bench\ls-env-before-2026-11-14.txt`.
   - In-game: the game's own upscaler at 67%, FG 2x, frame rate cap off. Anti-Lag 2 is optional.
3. For a test with you watching the screen: `RX_VK_READBACK_LATE=newest,3980`. That range holds most of the remaining readback wait.
   - Watch for white flashes.
